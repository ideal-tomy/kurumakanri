## 1. このアプリは何か（認識の確定）

### 一言

> 整備工場のオーナー／事務スタッフが、**車検・オイルの案内を見落とさず、確認してから手動で送り、顧客に見積を見せるための運用ツール**（Shaken Notify）。

### であるもの / でないもの

| である | でない（今は） |
| --- | --- |
| 週次の「案内作業デスク」 | 予約カレンダー本体 |
| 誰に・いつ・何を送るかのオペレーター | 整備工程・写真・在庫管理 |
| LINE / メールでのリマインド＋見積リンク | 会計・請求の本システム |
| 顧客向けの見積・車両状態の閲覧ページ | 全自動マーケ（自動送信は将来・既定 OFF） |

### 想定ユーザーと使い方

| 項目 | 内容 |
| --- | --- |
| 主ユーザー | 店舗オーナー、フロント／事務（非エンジニア） |
| 端末 | **ほぼスマホ片手**（店頭・移動中） |
| 頻度 | 週1回程度のまとめて作業＋都度の個別送信 |
| 規模 | 1店舗・顧客おおむね 200 名まで |

### すでに「それでよい」機能（大きく触らない）

- LINE に載せる見積・案内文面 → **オーナーが後からテンプレを出す想定。管理画面のテンプレ編集で変更すればよい**
- 見積の明細 → **手動編集できるので、送信前の微調整は現状で足りる**
- 送信そのもの・履歴・冪等（二重送信防止）の仕組み

**直したいのは「それ以外が分からない」状態**（どこを見ればよいか、今日やることは何か、詰まりをどう直すか）。

## 2. オーナーが達成したいこと（ジョブ）

週次オペを言語化すると次の5つ。

```text
1. 今週、誰に案内すべきか分かる
2. 文面と金額を確認して、間違いないものだけ送る
3. LINE（必要ならメール）で届ける
4. 失敗したら直す／再送する
5. 顧客がリンクから見積を見て、来店・予約につながる
```

付随ジョブ（主役ではないが止まると送れない）:

- 顧客・車両マスタのメンテ
- **公式 LINE 友だちと顧客の紐付け**
- 見積のたたき台作成（自動生成＋手動修正）

## 3. 理想の UI/UX 原則

認識が「案内オペレーター」なら、画面は次に従う。

1. **ホーム = 今日／今週の仕事**（緊急度順・要対応件数）
2. **1画面1ジョブ**（送る／直す／紐付ける）
3. **片手で識別できる情報密度**（ナンバー・残日・LINE可否が切れない）
4. **詰まりはホームから消えない**（送信失敗・LINE未紐付）
5. **タップ領域は下限 44px。画面を巨大ボタンで埋めない**（読めて進める密度）
6. **初見の店舗スタッフが、説明書なしで週次を一周できる**

### いまのズレ（なぜ「変な方向」に見えたか）

| 仕様上の自己認識 | いまのスマホUIが伝えていること |
| --- | --- |
| 週次の案内オペレーター | 機能メニューのショーケース |
| 今週やる仕事 | 5種類の巨大フォルダ |
| 詰まりを直す | LINE未紐付がフッター外で見つからない |
| 顧客を見分ける | ナンバーが切れて読めない |
| 失敗を直す | 履歴の上半分が巨大な「ホームへ」 |

→ **認識は正しい。UI が認識に追いついていない。**

## 4. シナリオ案（理想の1週間）

### シナリオ A — 月曜朝の週次（メイン）

**登場人物:** オーナー（スマホ片手）

1. アプリを開く → **ホームに「今週やること」が見える**
   - 例: 満了後フォロー 3件 / 90日以内 2件 / LINE紐付け待ち 1件 / 送信失敗 0件
2. いちばん赤い（緊急な）枠をタップ → 候補リスト
3. 先頭の顧客を開く（またはリストから「送る」）
   - 車種・ナンバー・残日・LINE可否が一目
4. 送信シートで金額・文面を目視 → 問題なければ送信
5. 必要なら見積明細だけ直して再プレビュー → 送信
6. 失敗がホームに出ていれば履歴へ → 理由を見て再送 or 電話
7. LINE紐付け待ちがあれば、友だち追加した人と顧客を結ぶ → その後送信可能に
8. 終わり。所要イメージ: **15〜30分**

**成功条件:** 「今週誰に送ったか／送れなかったか」が自分で分かる。説明書を開かない。

---

### シナリオ B — 店頭で友だち追加した直後

1. 顧客が公式 LINE の QR で友だち追加
2. ホーム（または目立つ導線）に **「LINE紐付け待ち」** が増える
3. オーナーが氏名・ナンバーを聞いて、一覧から既存顧客に紐付け（または新規登録）
4. その場でテスト送信 or 次回週次で案内

**成功条件:** Developers コンソールを開かない。`/line/unmatched` という裏画面を覚えていなくてもたどり着ける。

---

### シナリオ C — 個別に「この人に今送りたい」

1. 顧客タブで名前またはナンバーで探す
2. 詳細またはリストから送信
3. 見積が古ければ明細を直してから送る

**成功条件:** 名簿として使える（識別情報が読める）。送信導線が埋もれない。

---

### シナリオ D — 顧客側（受け手）

1. LINE のリンクをタップ
2. お車の状態・見積概要がすぐ分かる（店舗名も）
3. 詳細・印刷、電話／問い合わせができる

**成功条件:** ログイン不要。スマホで読める。店舗が誰か分かる。

## 5. 画面ごとの理想像（代表導線）

### ホーム（フッター中央）— 「仕事の入口」

**今:** 通知の種類が5つの巨大タイル  
**理想:**

- 最上段: **要対応**（LINE紐付け待ち / 送信失敗）※0件なら小さく
- その下: **今週の案内候補**（緊急度順の短い行。件数＋ラベル）
- 巨大タイルではなく、**1行＝1ジョブ**（ラベル左・件数右・緊急度の色）
- 補足: 「送付する相手を選んで確認へ」は短く残す

### 顧客（フッター左）— 「探す・紐付ける道具」

**今:** カード高く、ナンバー切れ、LINE状態が見えない  
**理想:**

- 氏名の下に **ナンバーを優先表示**（切れない）
- LINE 可否の小さな印（紐付済 / 未）
- 残日・状態バッジは邪魔にならないサイズ
- 密度を上げ、一覧で多くの件を見られる

### 履歴（フッター右）— 「詰まりを直す」

**今:** 上部の説明＋巨大ホームボタンがリストを圧迫  
**理想:**

- 失敗が先に目に入る（フィルタ既定や強調）
- ホームへの導線は小さく（または失敗0のときだけ案内）
- SUCCESS / FAILED の読み方が一発で分かるバッジ整理

### LINE 紐付け（ホームから到達）

**今:** 機能はあるがスマホ主ナビに無い  
**理想:**

- ホームの要対応から一発
- 文言は店舗語（例: 「友だち追加済み・未登録」）
- 「誰をどの顧客に結ぶか」が一画面で完結

## 6. 直す／直さないの切り分け

### 直す（認識とUIのギャップ）

| 優先 | 内容 |
| --- | --- |
| P0 | ホームを「今週の仕事」に作り直す（密度・緊急度・要対応） |
| P0 | LINE 紐付けをホームから見えるようにする |
| P0 | 顧客カードでナンバー等の識別情報を読めるようにする |
| P1 | 履歴を「失敗直し」に寄せ、無駄に大きい導線を減らす |
| P1 | 片手操作前提の余白・文字サイズ・タップ下限のバランス |

### 今は大きく触らない

| 内容 | 理由 |
| --- | --- |
| 通知テンプレの中身 | オーナーが後から出す。編集UIはある |
| 見積明細の手動編集 | 送信前調整として十分 |
| 送信 API・冪等・履歴の基盤 | 動いている。UIの見せ方が問題 |

### 本番構築とは別レーン

- クライアント名義の Supabase / LINE / Vercel
- テンプレ文面の店舗寄せ
- 法定費用・整備単価の実データ

→ [本番環境構築ガイド.md](./本番環境構築ガイド.md) 側。UI 認識の修正と並行可能。

## 7. デザイン判断のチェック質問（実装前に毎回）

新しい画面・改修を入れるとき、次に Yes なら進めてよい。

1. これは「今週の案内オペ」のどのステップを楽にするか？
2. スマホ片手で、説明なしに次の一手が分かるか？
3. ナンバー／残日／LINE可否など、識別に必要な情報が切れていないか？
4. 巨大ボタンで情報を犠牲にしていないか？
5. 詰まり（失敗・未紐付）がホームから消えていないか？
